MOOT — the switch that can never be flipped on

Big programs have hundreds of little on/off switches. Some of them are broken in a way nobody notices: they can never turn on, no matter who is using the program. This tool proves which ones, instead of guessing from how often they were used.

Feature flags are rules-as-data: an enabling condition is a predicate over a finite context. MOOT runs five audits over that reflection — unreachable, shadowed, tautological, contradictory, dependent — each with a derivation tree, and checks every verdict against exhaustive enumeration of the whole context space.

the problem

Counting how often a switch was used tells you almost nothing

"Not seen in the logs" is statistics, and it lies at low traffic

Imagine a light switch in a room nobody has walked into for a month. Is the switch broken, or has nobody tried it? You cannot tell by watching the room. That is exactly how teams decide which switches to delete — and every so often they delete one that worked, and something important breaks.

MOOT does something different. It reads what the switch is wired to and works out, by reasoning, whether any person in any situation could ever flip it on. If the answer is no, it shows you the wiring that makes it impossible.

A flag guarding an enterprise-only path in one region may legitimately see no traffic for a month, and a flag that cannot be on looks identical in the dashboard. Usage is the wrong instrument. The right question is structural:

is there any context at all in which this flag can be on?

A flag already IS a rule-as-data — the config file is its reflection, with no annotation needed — so this is boot.rofl's faculty, which judges a loaded program using its own rules over that program's reflection, pointed at a domain.

the answers

Five ways a switch can be dead

Five verdicts, each with a derivation tree

unreachable

No person, anywhere, in any situation, can turn it on. The wiring contradicts itself.

The condition is satisfiable by no context at all — including transitively, through a flag it depends on.

shadowed

A second rule that never gets a turn, because an earlier rule already covers everybody it would have covered.

Another clause admits every context this one admits. Entailment between rule bodies, not overlap.

tautological

The switch is always on. Somebody deleted the condition and left the switch, so the code still pretends it is optional.

A clause that constrains nothing and needs nothing. The flag is effectively deleted; the branch is not.

contradictory

Two switches that are supposed to be mutually exclusive are both on for the same people. Which one wins is an accident.

Two flags declared exclusive whose clauses admit a common context. Behaviour there is decided by the order of the branches, not by any condition.

dependent

The switch does not really decide anything: some other switch decides for it.

Every usable clause of F requires G. Deleting G kills F, and F's own predicates are theatre.

the proof

"Why can't it turn on?" — answered without shipping anything

whynot: the question people currently answer with a canary

Today the way to find out is to switch it on for a few real users and watch. MOOT just reads the wiring and tells you: which condition, in which rule, and what you would have to change.

Two clauses, two different causes, both named. The recursion through the requirement chain is whynot's own; nothing in MOOT arranges it.

Read it from the bottom: the second rule asks for the channel to be dev and also canary, and nothing can be both. The first rule needs another switch, and that switch has the same disease.

Clause 1 dies on a requirement whose own condition is empty; clause 2 on a pair of conditions sharing no value. Deleting either condition of the pair revives the clause, and the report says which.

the subtle one

Three rules that each look fine

An emptiness no PAIR of conditions explains

Sometimes no two conditions contradict each other — but all three together leave nobody at all. Three people each narrowed the list once, and nobody noticed that between them they had emptied it.

A pairwise conflict is sufficient and not necessary. The proof is the intersection itself (empty(C, D)); the pair is only the sentence, and when there is no pair the report says so rather than inventing one.

  loyalty_banner:  segment in free trial; segment in trial pro; segment in free pro

    "segment in free trial" admits {free, trial}
    "segment in trial pro" admits {pro, trial}
    "segment in free pro" admits {free, pro}

  every PAIR of them intersects. All three together do not, and
  conflict/4 correctly names no pair: true

A linter that greps for contradicting pairs misses this flag entirely.

the useful answer

And for a switch that does work: exactly who turns it on

Best-derivation: not "reachable" but a context you can paste

"It works" is not much use. "A team-plan customer in the US on version 11 sees it" is a thing you can put in a test.

The search over coalitions of clauses is host code — v0 has no choice operator — but every set it intersects is the engine's admits/3, and the answer is handed straight back to the engine to prove. The tree bottoms out in the same per-dimension sets the audits used.

reflection

The tool, pointed at itself

Rules-as-data judging rules, including its own

The rules MOOT uses are stored the same way the switches are. So MOOT can be pointed at a set of rules — including the rule set that checks every program in this project — and asked the same five questions. It found something.

The mapping is not an analogy: a relation is a flag, a rule concluding it is a clause, one body element is a condition over {yes, no}, and a positively-read relation is a requirement. Four of the five verdicts transfer; contradictory does not, because a rule set declares no mutual exclusions.

  22 rules encoded as clauses over 38 dimensions, 29 relations as flags

  unreachable relations: asserted_by forged imports
  rules that can never fire in this store: 3
    r0145d338  sees[main](?P,?Q)@now :- imports[main](?P,?X)@now, sees[main](?X,?Q)@now
    r66afcc0f  forged[audit](?F)@now :- asserted_by[main](?F,?Who)@now, in_perspective[main](?F,?P)@now, not authority[main](?P,?Who)@now
    rfc45fb4a  sees[main](?P,?Q)@now :- imports[main](?P,?Q)@now
  shadowed rule pairs: (none — no rule body of boot.rofl is a subset of a sibling)

What that means. One of those rules is the project's own forgery alarm — it is supposed to shout when somebody writes a fact they were not allowed to write. It reads a piece of information that nothing in this program ever produces. So the alarm has never been able to go off. It has been answering "all clear" to everything, including things that were not clear.

forged[audit] cannot fire. It reads asserted_by, which the kernel emits only when an assert names a who, and nothing in this store does. The audit has been answering "clean" to every program in the repository, and it would answer "clean" to a forged fact too. Not a bug in the rule — a rule with no input, and invisible to every test that asserts the audit is empty.

The same for sees: two of its three rules read imports, which boot.rofl declares edb and nothing populates, so visibility is reflexive only and the leak audit is weaker than its text suggests. Assert one authored fact and the verdict flips — and the forgery audit's first act is to catch it.

Pointed at its own rules, MOOT finds its evaluator layer dead: the one input a caller supplies per query is a context, and in a world where nobody asked about a context there is none.

the boundary

When this stops working

Decidability: finite domains, unary constraints, and where SMT starts

This only works because the tool knows every possible situation in advance: five lists of choices, spelled out. Six kinds of customer times eight regions times twelve versions times ten rollout slices times four release channels is 23,040 situations, and a computer can simply try all of them. If one of those lists were endless — every possible moment in time, say — there would be nothing to try, and the tool would have to guess.

Two hypotheses carry the whole design. Every dimension is finite and declared (dim/1, dom/2), and every condition constrains exactly one of them. It follows that the contexts a clause admits are a PRODUCT of per-dimension sets, and therefore:

questiondecomposes as
is this clause satisfiable?no single dimension of it is empty
does C1 contain C2? (non-empty C2)on every dimension, admits(C2) ⊂ admits(C1)
do C1 and C2 overlap?they meet on every dimension

Neither hypothesis is about the operators. version >= 7 is a comparison and stays inside them, because on a finite domain it denotes a finite set that moot.rofl enumerates with an ordinary rule. What breaks it is an UNBOUNDED dimension (a timestamp, a float): no product to walk. Or a constraint RELATING two dimensions (bucket < version * 8): contexts(C) is no longer a product, so per-dimension emptiness is neither sound nor complete. Past those, the answers need SMT and stop being complete.

One guard is worth naming: the per-dimension decomposition of containment is valid only for a NON-EMPTY clause, because the empty set is contained in everything while its per-dimension image is not. contains/2 carries that guard explicitly, and a dead clause gets the better verdict (unreachable) instead.

the check

Every situation, tried

A complete oracle, not a sample

To be sure the reasoning is right, the demo also does it the slow, stupid way: it walks through all 23,040 situations for all 52 switches — 1,198,080 checks — and compares. Everything the reasoning claimed held up.

Exhaustive enumeration in plain TypeScript, sharing no rule with the engine. Because the space is finite and declared, that walk decides every question asked here — so it is a complete oracle, and it also measures what the structural rules do NOT claim.

Two things the enumeration finds that the rules deliberately do not claim, and both are the point rather than an embarrassment. search_rerank is on in all 23,040 contexts, and no single clause of it is total: two partial segment lists cover the space between them. DNF tautology does not decompose per dimension (it is co-NP-hard in general). And bulk_export is on only where data_lake is, yet is not dependent on it — its first clause never asks for it. That implication is an accident of two condition sets, not a contract, and it evaporates the moment either is edited. dependent/2 reports the contract; enumeration reports today's coincidence.
