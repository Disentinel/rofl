ROFL · example

YAK — the rules you leave behind

When you have a question about a big pile of code, you can write a tiny rule that answers it. Most of those rules you throw away straight afterwards. Here are ten real ones from a single day of work — including the ones that were wrong, and one that should never have been written at all.

Every other example here demonstrates the engine. This one demonstrates working with it: rules-as-data written mid-task, an ontology that sediments instead of being designed, and the hygiene that stops a rule pile turning into a linter nobody reads.

the problem

Usually you have to build the map before you are allowed to ask directions

The model is required before it pays off

Imagine you are only allowed to ask a question about your city if you first draw a complete map of it. Most people would just never ask. That is what the serious code-checking tools feel like: you have to describe your whole program in their language before any of it helps you, and that work happens now while the payoff happens later, maybe.

There is another way round. Do not draw the map. Solve today's problem, and on the way, when a question comes up, write the smallest possible rule that answers just that question. Keep the answer. Usually throw the rule away. Do that a hundred times and a map appears anyway, without anybody sitting down to draw one.

This is what every formal method runs into. TLA+ wants the process rewritten. CodeQL wants queries written in advance, by people not working on your bug. Expert systems want a year of knowledge acquisition first. The investment is up front, the return is later and not guaranteed.

Writing scanners as you go inverts it. You are not building a model; you are solving a task and leaving a rule behind. The unit cost is minutes, not a sprint, and each step is paid for by the task that demanded it. The ontology of a subsystem is not designed — it sediments.

What changes is not quality but frequency. If a new query costs a ticket and a week, you ask a handful a year. If it costs three minutes, you ask two orders of magnitude more. Against grep the bar is lower and meaner: grep finds text, a scanner finds what is derivable — transitive dependencies, combinations of conditions, the things a regex cannot say — and grep leaves nothing behind.

the rule that governs this page

Everything here really happened

Nothing below was composed

It would be very easy to make these up, so we did not. Made-up examples always work out nicely, because whoever wrote them decided how they end. That makes them more convincing than real ones, which is exactly why they are banned here. If something has never actually happened, it does not get a story — it gets one line in a list at the bottom. An empty box is more honest than a filled one.

Fragments must be records of real runs, not written text. Invented fragments look more convincing than real ones, which is precisely why they are forbidden. If a mode has no real run behind it, no fragment is written for it: it goes as one line into “what to expect” at the end. Every fragment below names an artefact, and demo.ts re-runs the nine that still run.

Two provenance labels are used, and both mean a real run happened: caught — it happened on its own during real work; and provoked — reproduced on purpose, where the going-there was deliberate but the run was not staged. A third label, predicted, would mean “described, never reproduced”. No predicted mode is written up as a fragment; a test enforces it.

fragment 01 · the payoff

A rule that kept working after the person who wrote it had moved on

Sedimentary success — the only real return

01 a typo that cannot be seen kept

task
Make a tool explain which step of a chain threw a line away.
Make the HUH pipe demo say which stage ate a log line.
the question that came up

Somebody wrote a rule that used a word the system did not know. Instead of complaining, the system quietly treated that word as a thing that simply never happens — so the rule was always silent, and silence looks exactly like “nothing to report”. How many other rules in the program are silent like that?

hit(N) :- msg(N,S), contains(S,"404"). loads clean and hit is silently always empty: contains is not a builtin, so it parses as an ordinary relation with no rules and no facts. Every mistyped builtin becomes an unpopulatable relation. How many relations in a program can never hold a fact at all?

the scanner, whole
undefined_premise[audit](R, Rel) :- premise_pos(R, Rel),
                                    not concludes(_, Rel), not edb(Rel).

Positive premises only: an unpopulatable negated premise always succeeds, so it hides nothing.

what happened next

The rule was kept. Months of code later — well, hours, in this case — somebody else wrote a completely different program, and the old rule spotted the same kind of silent hole in it, without anyone asking it to.

The rule went into boot.rofl with a test and stayed. Replayed now across the six rule files shipped after it, it fires on one:

examples/moot/moot.rofl    load=ok   undefined_premise: (none)
examples/blam/blam.rofl    load=ok   undefined_premise: changed
examples/bleep/bleep.rofl  load=ok   undefined_premise: (none)
examples/drip/drip.rofl    load=ok   undefined_premise: (none)
examples/wtf/wtf.rofl      load=ok   undefined_premise: (none)
examples/spat/spat.rofl    load=ok   undefined_premise: (none)

changed/1 is BLAM’s diff relation, supplied by its host at runtime, and blam.rofl declares no inputs — so the rule file alone is mute, and that cannot be told apart from a misspelling by reading it. moot.rofl, written the same day, declares its twelve inputs and cites this audit in its header.

the check on the check

Five of those lines say “nothing found”. That is only worth believing if the rule is capable of finding something, so we broke one program on purpose and made sure it noticed. It named all twelve holes.

Five (none) rows prove nothing unless the instrument can say otherwise. Strip MOOT’s declarations and the audit names all twelve relations — so the empty rows are measurements, not a broken instrument.

A rule earns its keep by firing on code its author never saw.

fragment 04 · the dangerous one

The search that found nothing — because it never looked

False miss: the failure that agrees with you

A wrong answer that says “look at this!” is annoying, and you check it. A wrong answer that says “nothing here” is much worse, because you nod and move on. This is one of those.

A false positive argues with you; a false miss agrees with you. That is why it is worth twice as much attention and why a catalogue without one is lying.

04 “this file has no exports” discarded

task · question · scanner

Review a newly written source file before landing it. What does it export? Run grep.

what it returned

Nothing.

what happened next

It was read as “this file exports nothing”. Wrong. The file had one invisible character in it — a byte that is not really a letter — and that made the search tool decide the file was not text at all, so it skipped it. Without saying so. Every other check agreed everything was fine.

Read as “no exports”. False: the file held a literal NUL byte — a separator constant written as the raw character instead of the escape — and a grep that skips binary files skipped it in silence. No warning, empty stdout, exit 1. tsc was clean, the file’s own eleven tests were green, the kernel vocabulary check was clean because it only scans src/. Only git objected, calling a TypeScript source Bin 0 -> 7930 bytes and refusing to diff it.

Provoked here on two files identical but for one NUL, with the same question put to two invocations:

   instrument             clean.ts         withnul.ts
   /usr/bin/grep -c       3  [exit 0]      3  [exit 0]
   /usr/bin/grep -I -c    3  [exit 0]      (NOTHING AT ALL)  [exit 1]

Same file, same question, two versions of the same tool, opposite answers — and the quiet one is the one you get by default.

The sting is in which row you get by default. Typing grep does not name a program; it names whatever the environment has bound, and in this shell that is a wrapper with -I already applied. The silent row is the ordinary one.

fate

The narrow scanner discarded, replaced by a gate that reads bytes rather than lines and runs in CI. Its own test plants a NUL to prove the gate can say no — and it rejected its author on the first run.

A negative result is a fact about the instrument until a positive control says otherwise.

fragments 06 and 07 · the same afternoon

A rule we kept too long, and a rule we should not have written

The stale model, and the case for not writing a scanner at all

06 the probe outlived its subject discarded

the question

Earlier someone measured that the order things arrive in makes the program five times slower. We re-ran that exact measurement to see if it was still true.

A recorded finding says the store’s quadratic insert is not a property of the index but of the order keys arrive in: measured at 64k facts, ascending 132 ms, scrambled 505 ms, shuffled 716 ms — a 5.4× spread. Does it still hold?

what it returned
  integer args (lex order is scrambled)         102 ms
  zero-padded (keys strictly ascending)          84 ms
  zero-padded, shuffled arrival                  88 ms
  spread: 1.2x     (recorded when this probe was written: 5.4x)
what happened next

The rule still ran perfectly. It was just no longer about anything: somebody had fixed the thing it was watching, so all three cases now go down the same path. A person trusting this rule today would conclude the exact opposite of the truth — that the order never mattered — when in fact it mattered so much it got engineered away.

The probe survived; its subject did not. src/store.ts grew an append-then-merge index citing the performance invariant by name, so all three arrival orders now take the identical append path and the spread is absent by construction. A reader trusting this probe today would conclude the opposite of the truth.

A kept scanner with no owner goes on answering. It does not go on being about anything.

07 the scanner was not needed discarded

the question

Did the slowness really go away, or had our measurement just gone blind? Good question — so we built a second, cleverer measurement to find out.

“No spread” has two readings: the effect never existed, or the probe can no longer see it. Fragment 04’s rule applies here to us, so: build the positive control, forcing the one path the index still splices on.

what it returned

Nothing useful. The first run did not finish inside two minutes. We made it smaller and ran it again, and it still could not tell the two possibilities apart. About four minutes gone and the question still open.

At 64k it did not finish in two minutes. Resized to 16k: 6.1 s / 6.1 s / 7.4 s — a 1.2× spread, the same non-answer, because an O(n) read per write swamps the splice it was built to expose. Two runs, two resizes, four minutes, question still open.

what happened next

The answer had been sitting in the code the whole time, written out in plain English in a comment, about fourteen lines long. Reading it took under a minute and settled the question completely.

The answer was in src/store.ts, lines 29–42, in English, in a comment left by whoever landed the fix:

Inserting one key at a time into a sorted array is free at the end and
a memmove of the tail anywhere else, so the cost of a fact is decided
by the ORDER facts arrive in. [...] Arrivals are appended instead, and
the run is put back in order once, for a batch, by `absorb`.

The scanner was not needed. Reading the code would have been faster.

When not to write one. Do not write a rule when your question is “what does this one bit of code do” and you can just open it and look. Rules are for questions where the answer is spread across lots of places, or buried in more data than you could read yourself — those are the ones no amount of looking will answer.

The criterion of abstention. Abstention is a mode of work, not the absence of it, so it needs a criterion rather than a wish. Do not write a scanner when the question is “what does this one named function do” and the function is open in front of you: measurement is the wrong instrument for a question whose answer is a mechanism rather than a quantity. A scanner earns its cost when the question is about behaviour emergent over many sites, or over data too large to eyeball — both of which resist reading precisely because no single place contains the answer.

Without this fragment the demonstration would be unfalsifiable. A method that always helps is advertising.

fragment 10 · the name

The day that got eaten

Yak shaving proper — no scanner, no recovery

Yak shaving is what people call it when you set out to do one thing and end up four steps sideways doing something else entirely. The name of this example admits that, so it has to show one.

The name obliges. This fragment ends badly, with no recovery and no rule to discard, because none was ever written — and that is the fragment.

10 enforcing a check that protected nothing discarded

task

Ship three demo examples.

the detour

A written rule said “always run both test suites”. So every helper was told to run both. Then a whole round of work went on worrying that the slower suite would blow the time limit — and the slower suite was already being run automatically somewhere else. Nothing needed protecting. The worrying cost about five minutes per helper, three helpers at a time.

“Both runners green” went into all four subagent briefs. Then a whole turn went on predicting that the new demos would push the slow runner past its budget — while that runner already had its own CI job, so nothing local was being protected at all. Cost: about five minutes of dead verification per agent cycle, three agents in parallel, 295 s against the other runner’s 117 s.

and then it compounded

Trying to stop it made it worse. The helpers could not hear the message to stop while they were busy, and stopping them by force looked to them like a crash, so they started over. A fourth run began minutes after the third was killed. The machine was so overloaded that every measurement taken during that stretch was wrong and had to be taken again.

A message reaches a subagent only at its next tool round, so three countermands sat undelivered while three agents sat inside runs. Killing a child does not cancel the intent — it reads as a failed run and triggers a retry — so a fourth started minutes after the third was killed. Load hit 111 on 4 cores, and every timing taken in that window was inflated and had to be re-measured before it could be quoted.

fate

No rule to discard. What the detour left behind is a one-paragraph correction to the project’s own instructions, naming the measured numbers and separating “green in CI” from “run both by hand”.

The detour is only paid for by the artefact it leaves; here it left one, and the thing it set out to protect never needed protecting.

the rest of the catalogue

The other five, briefly

Fragments 02, 03, 05, 08, 09

02 · redefining

The question was “count all the ways to make this thing”. Writing the counter down proved the answer was “infinitely many”, so the counter was never finished. Working out what the question meant was the answer.

“Enumerate the derivations and check the count” does not terminate on a cyclic graph. Formalising it forced the replacement question — can “infinitely many” be decided? — answered by twenty lines of Tarjan over the support hypergraph. The enumerator was never written. The value was the definition, not the computation.

03 · quick

One question, four experiments, one table, three minutes, then straight in the bin. The table is still being used.

Four mutations against seven meta relations settled a cache’s invalidation key exactly: the expensive layer turned out to be completely immune to data and to need only the rule ids. Probe deleted the same day.

05 · diverging

Asked “how many ways can this be true?” and got “infinite” for something with exactly one cause. The machine was right; the question had quietly changed meaning — and the question is what got fixed. The same probe now answers “one”, and it stayed in the drawer as the thing that would notice if “infinite” ever came back.

The carry idiom makes every persisted fact its own support one tick back, so the counting semiring answered INFINITE for a fact that cites nothing. The engine was not wrong — it answered about a support graph that contained time travel. Settled by narrowing the question rather than the arithmetic: the fold is about ONE tick, so a carried fact is a given in it. The probe is unchanged and still runnable; it grew a control line, because INFINITE=0 would also be printed by a fold that walked nothing and by one that stopped detecting cycles. The control puts both loops in one store — carried fact 1, cycle inside the tick INFINITE — and rejects both mutants.

08 · an accident

A check compared everything byte for byte and said the change was safe. It was not: the check only ever looked at three very simple programs, which happened to be the ones lying around.

A byte-identical golden capture certified a change that then failed nine tests. Measured after the fact: every program in the golden set stops at one stratum boundary; the program that broke has fourteen. A golden is a substitute for a diff, never for coverage.

09 · wrong premise

Someone reported a bug. We wrote a rule to confirm it, and the rule proved the bug was not there — which is how we found the real one, which was different and better hidden.

A report claimed facts vanish from the fold. They do not. Refuting the stated symptom is what surfaced the actual defect: a renaming counter leaking into the firing signature, inflating one derivation into two supports while the Boolean verdict stayed correct.

hygiene

How do you stop ending up with three hundred rules nobody trusts?

Accumulation hygiene, and the part it cannot reach

This is the obvious worry. Write a rule every time you have a question and in a year you have a mountain of them, half of them wrong, and everybody ignores the lot. That is the life story of every code-checking setup anyone has ever had.

Three hundred rules nobody trusts is the fate of every linter with an accumulated configuration, and the remedy has to be mechanical rather than well-intentioned.

The answer is to point the same machinery at your own rules and ask which of them are dead. Here is it doing that:

The instrument already exists: MOOT pointed at the accumulated scanner set — the same five verdicts (unreachable, shadowed, tautological, contradictory, dependent), turned on your own rules. It already points itself at the kernel’s audit layer, so this reuses it rather than growing a second one:

  22 rules encoded as clauses over 38 dimensions, 29 relations as flags

  unreachable relations: asserted_by forged imports
  rules that can never fire in this store: 3
    r0145d338  concluding sees
    r66afcc0f  concluding forged
    rfc45fb4a  concluding sees
  shadowed rule pairs: (none)

One of those dead rules is the forgery check. It looks for facts written by someone who was not allowed to write them — but nothing in this project records who wrote what, so it has never once been able to fire. It has been cheerfully reporting “all clear” for its whole life, and it would report “all clear” about a forgery too.

Fragment 01’s rule is not among the dead, which is what this pass was run to find out. forged[audit] is: it reads an input nothing here populates, so it has been answering “clean” to every program in the repository and would answer “clean” to a forged fact too.

And the bit this cannot check

The gap, which is the more useful half

Only one of the ten rules on this page is the kind of rule that check understands. The other nine are little programs, and the check has nothing to say about those at all — including number 06, the one that had quietly stopped being about anything. It still runs. It still answers. Nothing here notices. We do not have a way to catch that yet, and saying so is more use than pretending otherwise.

Of the ten scanners catalogued here, exactly one is a rule. The other nine are host-language probes against the store API — not an accident of this session, since the questions were about the engine, and a rule cannot ask how many milliseconds an insert took. MOOT decides rule-shaped scanners exactly and has nothing whatever to say about probe-shaped ones.

Fragment 06 is the proof. A probe that has gone stale is not unreachable, not shadowed, not tautological. It runs, it returns a number, and it is about nothing. No verdict in this pass catches it. The hygiene that would — does this probe still measure what its comment claims — is not mechanised anywhere in this repository, and naming that is worth more than a clean bill of health.

the empty cells

Things we expect to go wrong but have not seen yet

What to expect — reasoned about, not reproduced

These are ways this could go wrong that we have thought about but have not actually had happen. They get one line each and no story, because a story would mean making one up.

One line each, no invented session. As runs accumulate these should move up into the catalogue with a caught label — and the ones that turn out to be imaginary should be struck out instead.

  • a rule instead of a fix — formalisation as a substitute for the hard work; converging useful activity in place of solving the problem.
  • premature generalisation — a rule inferred from a single case.
  • burial under scanners — six months on, half the firings are false and everybody ignores all of them.
  • a rule that codes a snapshot — it matched today and is meaningless tomorrow. Fragment 08 is the corpus version; the snapshot version needs a repository with history and was not attempted.
  • approval without looking — an agent emits a rule with a plausible but wrong premise and a human agrees. Trivially provoked; not provoked here.
  • false positive — a rule written too broadly. The nearest real instance is inside fragment 02, where the naive rule condemns 18 harmless kernel facts, so it is written up there rather than given a fragment of its own.
  • a model extracted once while the code moves on — fragment 06 is the code-moved-under-the-probe form; the extracted-model form needs a prepared repository and was not attempted.

modes of work

Four modes, and the fourth is real work

reactive

question in a task → scanner → answer → usually thrown away. The common case.

retained

a scanner promoted to a standing check on diffs. Rare, and it has to earn it.

reflexive

the five verdicts turned on your own accumulated scanner set. Not a party trick — mandatory hygiene.

abstention

do not write a scanner. A mode of work, not the absence of one, with a stated criterion in fragment 07.
