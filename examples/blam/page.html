BLAM — what a diff hits, and why

Change one file in a big repository and a build system decides what to rebuild. It gets the answer right and then throws away the reasoning. This keeps the reasoning: which chain of dependencies dragged each thing in, which things were spared and where the search for them stopped, how many separate routes lead to each, and which single dependency to delete so it stops happening.

Explained without jargon.

1 Boxes built out of other boxes

A big software project is kept in one repository full of parts. Each part is a box, and some boxes are built out of other boxes. The website box is built out of the interface box and the data box; both of those are built out of the little box of shared helpers; and everything sits on one settings file at the bottom.

Now you change one file. Which boxes have to be built again? Every box that is built out of the box you touched, and every box built out of those, all the way up. That is all the computation there is, and every build tool does it correctly.

The interesting part is not the answer. It is that the tool cannot tell you anything about the answer afterwards.

A monorepo build graph: packages as nodes, dependency edges pointing at what a package needs. Every package has a build target and a test target, and the test target depends on its own build. Files are mapped onto targets, many-to-many.

The affected set of a diff is the reflexive-transitive closure of the reverse dependency relation over the targets that own the changed files. As a fixpoint: 

reaches(F, T)  <-  owns(T, F)
reaches(F, T)  <-  needs(T, U) ∧ reaches(F, U)
affected(T)    <-  changed(F) ∧ reaches(F, T)

Least fixpoint of a monotone operator over a finite domain; it converges, and Bazel, Nx and Turborepo all compute it. What none of them retains is the support: which rule instance, with which premises, put each fact into the set. Drop that and the set is an oracle you cannot cross-examine.

Two shapes in that picture do all the work later on. utils is reached by web in two different ways — through api and through ui — so there are two separate reasons web has to be rebuilt. And config at the bottom is needed by absolutely everything, so changing it rebuilds the entire repository.

Two features are load-bearing. The diamond utils → {api, ui} → web gives two edge-disjoint routes, so path counting exceeds one without anyone arranging it. The global config is reachable from every package, which is the commonest real pathology and the one an affected-set tool reports as a single word. docs is unreachable from a utils diff, which is what makes whynot have something to explain, and shared/schema/events.json is owned by two targets at once, which is what makes ownership many-to-many rather than a directory prefix.

2 The answer every build tool gives

One file changes — packages/utils/src/str.ts — and here is the whole of what you get: 

one file changed. 10 of 16 targets are affected:
  api:build api:test cli:build cli:test ui:build ui:test utils:build
  utils:test web:build web:test
spared: config:build config:test core:build core:test docs:build docs:test
cost:   915 minutes of the repository's 1057

Correct, and unarguable. Two questions get asked about it every single day, and neither has an answer anywhere in the tool:

  • Why is web on that list? Nobody touched it.
  • Why is docs not on that list? I am fairly sure I broke it.

The first makes people stop trusting the tool and rebuild everything by hand, which is slow. The second is the dangerous one: the thing you broke never gets tested, and you find out later.

The set is right; it is also the entire output. Two queries have no place to live:

  • why — the derivation of a membership fact, down to the axioms. bazel query somepath() gives you a path through the target graph, but only against a hypothesis you already formed, and it never connects the path to the file in the diff that started it.
  • whynot — for a target absent from the set, the front at which the closure stopped. Nothing answers this, because absence from a set carries no information about its own cause. Non-membership is where missed regressions live.

Read the bottom lines upward and it is a sentence: the file belongs to utils; api is built out of utils; web is built out of api. Every step is something you can go and check in the project's own settings, and each one is marked [axiom] — meaning nothing was inferred, it was simply written down somewhere.

Every leaf is a base fact: two pkg_dep edges, one owns, one changed. Nothing is elided, and the rule id on each internal node identifies which of the five clauses fired. This is not a report the demo constructs — it is the support the kernel recorded while computing the set, rendered.

4 Why did it not rebuild docs?

This is the half nothing else has, and the half that matters more. You believe you broke docs. The tool did not rebuild it. Asking why not gives you the exact place the search gave up:

whynot walks the same rules downward and names, per rule, the premise instances that failed, recursing into each until it bottoms out. The result is a stopping front, not an empty set:

Three statements, which together are the answer:

  1. docs does not own the file you changed.
  2. Neither of the two boxes docs is built out of was rebuilt either — and here is the same question asked about each of them.
  3. The bottom box, config, is built out of nothing at all, so there is nowhere further to look. That is where the search stops.

And now the useful bit. If docs really does use the file you changed, then the missing link is the bug — somebody forgot to write down that docs is built out of utils. Your change was never tested against it, and nothing would ever have told you. This is how you find that out on the day you make the change, instead of three weeks later.

The tree terminates on its own: no depth or node bound fires, which the test asserts, because a front truncated by a budget is not a front. rule r9c7a66bc: head does not unify is the needs(t(P,test), t(P,build)) clause being ruled out against a build target — structural noise, and deliberately not hidden, since a demonstration that silently skipped candidate rules would be a weaker demonstration.

The operational payoff: if the source really does import the changed module, the absent pkg_dep edge is the defect, and the front points straight at it. A missed regression is a non-derivability whose cause is a missing base fact; you cannot chase that with a tool that only prints derivable things.

5 How many separate reasons?

The same rules, counted instead of just checked. For each rebuilt box: how many different chains lead to it from the file you changed?

The counting semiring folded over the support hypergraph the kernel already recorded — ⊕ is +, ⊗ is ×, base facts annotate to 1. The value of a fact becomes the number of derivation trees for it, which here is the number of distinct dependency paths. Not one line of the rules changed.

targetroutes 
utils:build1
utils:test1
api:build1
api:test1
ui:build1
ui:test1
cli:build1
cli:test1
web:build2through api, and through ui
web:test2

A 1 means one chain: delete that one link and this box stops being rebuilt. A 2 means two chains that share nothing, so deleting either link changes nothing — the other one still drags it in. That number is a measure of how tangled a box is, and no build tool reports it.

Change the settings file at the bottom instead, and web comes out at 5. All sixteen boxes rebuild, and there are five separate reasons for that one.

One route means removing one edge stops the rebuild. Five means the target is wired into everything — a connectivity metric that computing the affected set never needs, and therefore never produces, but that the recorded support gives away for the price of one fold. Under the global config diff, web:build scores 5 and every one of the sixteen targets is affected.

Why this number is finite here, and would not be everywhere

Counting chains only works if the chains cannot run in circles. A build graph never does: if box A were built out of box B and box B out of box A, nothing could ever be built at all, so every build tool refuses such a project outright.

Put one circular link in on purpose and ask the same question, and the tool answers infinitely many — which is the truthful answer, and a completely useless one. That is why the reason for the number being finite is written down in the rules file, rather than quietly assumed.

The support hypergraph of reaches is acyclic because the package graph is, and the package graph is acyclic by construction — a cycle in it is a configuration error every build tool rejects at load. So the counting fold converges by plain Kleene iteration and needs no closure operator; the demo reports cyclic: 0.

The instance itself is nonetheless declared CLOSED and carries a star, and that is not decoration. Load one forbidden edge and the same instance says so:

A fact on a cycle really does have unboundedly many derivations, so infinitely many is correct — and useless. The Boolean verdicts are unchanged; only the metric died. That is the whole reason to state the acyclicity as a property of build graphs rather than of these rules: copy the rules into a cyclic domain and the counting stops meaning what you think it means, silently, with no error anywhere. examples/nope/ is the sibling case — an assume-role graph has cycles, and the count there is a number only because that model carries the path inside the fact.

6 In what order?

A third question off the same rules: how far is each box from the file you changed? That gives the order to build things in — what can start right now, and what has to wait.

The tropical (min-plus) semiring over the same support, charging one per rule firing: ⊕ is min, ⊗ is +, so a fact's value is the cost of its cheapest derivation. Divide out the constant and it is the number of dependency edges between the diff and the target.

Wave 0 can start the second the change lands. Everything in wave 1 waits for wave 0, and so on. Four waves, and the deepest wave is what decides how long you sit waiting.

Honest caveat: min-plus gives the earliest wave a target can be reached in, which is a lower bound on when it may start — not a schedule. A scheduler wants the longest path, since nothing may start before all of its dependencies finish. That is max-plus, a different instance, and it would be BOUNDED only because this graph is acyclic — the same caveat as counting, one step further along.

7 Which one link should we cut?

The question that turns a report into a decision. If you could delete one dependency from the whole project, which one buys the most? Not "which is ugliest" — which one, removed, stops the most rebuilding from ever being triggered.

The tool can answer that, because it knows every chain. A link is worth cutting for a particular box exactly when it appears on every chain to that box. If two chains avoid each other, cutting either one changes nothing.

The provenance semiring, with the base annotation carried only by the pkg_dep facts. A monomial of reaches(F, T) is then the set of package edges one route uses, and the polynomial is the set of routes. So the single-edge cuts for a pair are exactly the intersection of its polynomial, and an empty intersection is a proof that no single edge suffices. The needs(t(P,test), t(P,build)) edge comes from an unannotated fact and contributes the multiplicative identity, which is correct: you cannot stop a test depending on its own build.

Three things fall out of that table that you would not have guessed:

  • The link that disconnects the most things is not the link that saves the most time. Cutting cli → api untangles 14 pairings; cutting ui → utils untangles only 10 but saves nearly twice the waiting.
  • Three of the eleven links are worth nothing to cut. Every chain that goes through them has another way round, so removing them changes not one rebuild. They are free to keep and free to delete.
  • For web, the answer is that there is no single link. Its two chains share nothing — which is exactly what the 2 in the previous section was telling you. The same fact, seen twice.
  • Ranking by couplings and ranking by money disagree: cli → api cuts the most pairs (14) and ui → utils saves the most minutes (575). Only one of the two is anybody's actual question, and a tool that reported "affected set size" would have offered neither.
  • Three edges have an empty score: every route they carry has an alternative. A structural dependency review spends time on them; this ranking says not to.
  • The intersection for (utils/src/str.ts, web:build) is empty, matching the count of 2 — the connectivity metric and the cut analysis are two readings of one polynomial.

And the prediction is checked rather than asserted: the demo retracts pkg_dep(api, utils), re-runs the fixpoint from scratch, and compares. 

  $ retract pkg_dep(api, utils)   -- and re-run the fixpoint
  affected: 10 targets / 915 min  ->  6 targets / 720 min
  ui:build ui:test utils:build utils:test web:build web:test
  oracle: AGREE — the predicted blast radius of cutting api -> utils

8 Is it right?

Every number on this page is checked against a second, completely separate program that walks the same boxes by hand and counts the chains itself. It shares the list of boxes and links and nothing else — none of the rules, none of the machinery.

Then every one of the twelve files in the project is treated as a change in turn, and both programs are asked about all sixteen targets: is it rebuilt, and by how many chains?

The oracle is an independent memoized depth-first path count over the target graph, sharing only the base facts — no rules, no derived relations, no semiring. Every file as a single-file diff, against every target, on the verdict and on the route count. It throws rather than returning a wrong finite number on a cyclic graph, which is what makes it usable as the check on the cyclic variant too.

9 What this gives over Bazel

Honestly: by result, nothing. Bazel, Nx and Turborepo compute the same set, on real repositories, far faster. This is a toy graph on an engine that re-runs the whole fixpoint from scratch on every change.

By question, four they do not answer:

  1. Why did this get rebuilt — the chain, link by link, down to the file you touched.
  2. Why did this not get rebuilt — the place the search stopped, which is where a missed break is hiding.
  3. How tangled is this — how many separate chains reach it.
  4. Which one link to cut — and what it buys.

All four come off the same five rules and the same single computation. Nothing was added to get them; the tool simply stopped throwing the reasoning away.

  1. why — the derivation, every edge named. Not a separate query against a hypothesis you already have, but the support of the computation that was already run.
  2. whynot — the stopping front for a non-member. No build tool has this at all, because absence from a set carries no cause.
  3. counting — connectivity, from one fold over the recorded support.
  4. the cut — the intersection of a provenance polynomial, turning the report into a design decision.

Four questions off five rules that mention no carrier anywhere. The Boolean fixpoint, the count, the depth and the provenance are four folds over one support hypergraph, and the rules do not know which one is being asked. That is the actual claim; the affected set is just the price of entry.
