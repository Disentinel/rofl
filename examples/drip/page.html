DRIP — what goes dark if you delete this metric

A chart goes blank and nobody notices, because blank is not an error. This says which missing thing made it blank — the metric, one label value, or a rule four steps upstream — and what else goes blank if you delete that thing.

Explained without jargon.

1 The problem

A dashboard is a wall of charts. Somebody renames or deletes one of the numbers those charts are drawn from, and a chart just goes empty. Not red. Not broken. Empty — which looks exactly like "nothing is happening right now", so nobody looks twice.

The dangerous version is the alarm. An alarm that watches a number that no longer exists never goes off. You find out on the day it should have.

And the question in reverse is the same one. Before you delete a number, you would like to know what is standing on it. Nobody can answer that either.

Panels and alerts are queries over a namespace that changes underneath them. When a series disappears, the query does not fail; it returns an empty vector. Absence of data is indistinguishable from absence of events, so a broken panel and a quiet system look identical, and the failure is discovered by an incident rather than by a check.

Resolution is a least fixpoint over lineage: a query resolves if every selector resolves; a selector resolves if its metric exists and every label matcher is satisfied; a metric exists if it is scraped, or if the recording rule that writes it resolves — which is a query again. That recursion is why one dead scrape target can take out a panel four links away, and why the interesting output is not a boolean but the chain.

2 Why this one is cheap to build

Most tools like this need somebody to explain the meaning of things first. This one does not. Both halves of the comparison are already written down by machines:

  • the dashboards are files, and the names of the numbers are inside them;
  • the list of numbers that actually exist comes from the thing storing them.

Two dumb readers, no expert, no guessing. And you can check the answer for free: it says a chart is empty, so open the chart.

Extraction is deterministic at both ends. Dashboards are JSON; metric names and label matchers parse out of the query text; the live series list comes from the store's own label and series endpoints. There is no generative step and no annotation an expert has to supply, which is the layer that makes comparable tools expensive and arguable.

The two sources go into two ledgers, and the kernel keeps them apart. [repo] is written by the dashboard exporter, [store] by the metrics store, and every conclusion lives in [main] and reads both through declared imports. An exporter that would like a metric to exist cannot make it exist:

3 What is dark, and why

Ten things on these dashboards are showing nothing. The tool does not say "no data" — it names the missing thing, and there are four different kinds of missing thing:

  • the number is gone — somebody deleted it;
  • one setting on the number is gone — the number is fine, but the chart asks only for the part of it that came from a test environment, and that environment was switched off;
  • a step in the middle broke — the chart reads a number that another rule computes, and that rule lost its input;
  • it never worked — the chart has a typo in it and has been empty since the day it was written.

The classification is derived, not pattern-matched on the error text — there is no error text. Each row below is a relation (dark_missing_metric, dark_missing_label, dark_broken_rule, never_existed) that names its own link.

Four of those ten are alerts or SLOs. A dark panel is visible to whoever opens the dashboard. A dark alert is visible to nobody, until the day it was needed and did not come.

4 The label case, which is the whole difficulty

Here is the one that catches people out. The number the chart wants does exist. It is being written right now. The chart is still empty.

Because a chart does not ask for "the number" — it asks for a slice of it: requests from the canary environment that failed. The canary environment was decommissioned three weeks ago, so that slice has nothing in it, and the chart draws nothing.

A tool that only compares names would tick this off as healthy. That is why the settings — the labels — are in the model from the first line, and not bolted on later.

http_requests_total resolves. metric_ok holds all the way down. The selector carries {env="canary", status="5xx"}; status="5xx" is present and env="canary" is not, so matchers_ok fails at index 1 and the chain names the exact matcher. Notice that metric_ok never appears as a failed premise anywhere in this tree — the metric is not the break.

6 Blast radius: load-bearing against mention

Now the question in reverse. You are about to delete a number. What goes dark?

Two charts can use the same number and be hurt completely differently. A chart drawn from that number alone dies. A chart with six lines on it, one of which is that number, loses a line and keeps working. Both are "affected"; only one is an outage.

The distinction examples/oops draws between a citation that carries an argument and one that names a paper in passing. Here it is computed rather than declared: a consumer with a second, resolving query that does not itself need the metric survives losing it.

p_payment_gw_errors — DARK
its only query stands on the metric. Delete it and there is nothing left to draw.
p_exec_health — DEGRADED
one of six lines. Five still plot, and nobody opening the dashboard can tell that the sixth is missing.

The ORACLE line below is two independent computations of the same set: the derived answer reads the rules, and excise deletes the base fact and re-runs the whole program from scratch. The diff is the blast radius. Neither knows about the other.

This is where the model was wrong, and the oracle caught it. The first version had one feeds relation for both kinds of edge, and predicted that deleting queue_depth would darken p_capacity_headroom. It does not: the only route between them runs through a rule reading already-written samples — a real lineage edge, but not an availability one. Two metrics out of four disagreed. The fix was two relations, not one, and the disagreement is reported rather than tuned away.

7 Counting: how fragile is each chart

Count the number of independent things a chart is drawn from. One means that chart is a single point of failure — one deletion anywhere upstream and it goes blank. Zero means it already has.

The counting semiring folded over the support hypergraph: the value of consumer_live(C) is the number of derivations, which here is exactly the number of independently resolving queries. Twenty of thirty-one consumers have exactly one.

The reading of that count is domain knowledge and is stated on purpose: the identical metric means robustness in examples/nope and examples/oops, ambiguity in AKA, launderability in BLEEP, and fragility here.

8 The loop, and why counting survives it

One of the rules here smooths a number using its own earlier values, and two others feed each other. That is a loop. If you count "ways data can reach this chart" by walking the loop, you can go round it forever, so the honest answer is infinitely many — true, and useless.

The fix is to remember where you have been. A route that revisits something it already passed is not a new route.

The lineage graph is acyclic except for three past_input edges. Walking it, every trip round a cycle is another derivation and the counting semiring answers INFINITE — correct, and the wrong metric. Carrying the visited chain inside the fact makes a repeat impossible, so the value becomes the number of simple paths. This is the technique examples/nope uses for assume-role chains, and absent is positive rather than negated so the stratification checker never has to be argued with. 

lineage(Top, Top, cons(Top, nil)) :- metric(Top).
lineage(Top, M, cons(M, P))       :- lineage(Top, X, P), feeds(M, X), absent(M, P).

Rooted at a metric, not at a query: the root is then recoverable from the path, so each path has exactly one derivation. Rooting it at the query gives the same set of paths and multiplies every count by the number of queries that happen to share a root.

9 Dead series — the question nobody asks

The reverse audit. Which stored numbers is nobody looking at? Not "rarely looked at" — provably not looked at, by any chart or alarm, directly or through any rule. Somebody is paying to store those every month.

examples/moot's dead-rule audit pointed at data instead of rules: dead_series(M) :- series[store](M), not watched(M), where watched is the reflexive-transitive lineage over both kinds of edge, because a metric read only for its history is still read. The rule that computes a dead metric is itself dead, so the audit finds the CPU as well as the storage.

payments_gateway_errors_total is in that list — the metric that appeared. Nobody has moved a dashboard onto the new name yet, so by the model's own definition it is dead, and that is exactly the evidence that raises the rename guess in the next section to its top tier.

10 Rename is a guess, and it stays a guess

One number vanished and another appeared with the same shape two weeks later. That looks like somebody renaming it. It is not a fact, it is a hunch, and the tool says so — with a number attached to how sure it is.

More importantly: nothing else the tool says depends on the hunch. Delete the guess entirely and every verdict on this page is identical.

Three tiers of evidence, each a separate derivation of renamed_to, folded with the Viterbi semiring — which takes the best tier rather than the product, so confidence is the strongest evidence available and not what survives multiplying the weakest. The weights ride on the firing, so the ledger never carries a number nobody measured.

11 What it does not answer

A chart can be empty for reasons this tool cannot see at all — the thing collecting the numbers is down, the dashboard has no permission to read them, the numbers are older than what is kept, or the service simply is not running. The tool answers for the structural reasons only, and it says so in its own output rather than letting you assume it checked everything.

The covered classes and the uncovered ones are facts in the program (scope_covered, unmodelled_cause), so the boundary is printed by the tool and not only documented next to it. "Structurally fine" is the strongest verdict available here.

One further limit, measured rather than asserted: dead_series holds because nothing watches the metric, finite failure carries no annotation, and so the provenance fold names the presence and never the absence. That is printed in the demo's own output too.

12 Checked against something that is not the engine

A tool that only agrees with itself has proved nothing. So the same question is answered a second time, by a short piece of ordinary code that shares the raw data and none of the reasoning — and the two answers are compared, chart by chart.

An independent re-resolution of every consumer against the live series list, in plain TypeScript: it reads the EDB relations back out of the store, never touches a derived one, and is a worklist and two loops. The suite also runs it on a fixture it has not seen — delete a live metric in both worlds — because an oracle that agrees on one fixture proves very little.

A rule outside range restriction is evaluated top-down; the boolean answers stay correct and every count above would then be folded over a different fact set than the verdicts describe. That is asserted, not assumed.
