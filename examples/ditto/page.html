DITTO — prove the refactoring preserved what it promised

Somebody says "I only tidied it up". Pin the model of the code before the edit, re-read it after, and check the exact list of things the edit said it would not touch. Not "behaviour is identical" — that cannot be proved, and promising it is a lie.

Explained without jargon.

1 The problem

Imagine a big machine made of small parts, and somebody rearranges the parts to make it tidier. They promise the machine still does exactly the same thing.

How would you check? Today you press a few buttons and see if the right lights come on. If they do, everyone says "fine". But you only pressed a few buttons, and the machine has thousands.

What nobody checks is the wiring. A wire can be unplugged and all the lights you happened to press still come on — until the day you need the one that does not.

"This is a refactoring" is an assertion nobody checks. Tests check sampled outputs on sampled inputs. Nothing checks structure, and nothing lets the author say which subset of the structure was supposed to survive.

A refactoring is an equivalence class, and different refactorings preserve different things — extract-method preserves external behaviour and reachability while changing internal structure, a rename preserves everything but identifiers, a module move preserves dependencies while changing file layout. Existing tools cannot express "this may move and that may not".

The prior art is dense and it all does the same thing: characterization tests and golden master, snapshot testing, contract testing, differential testing, shadow traffic and request replay, GitHub Scientist, Twitter Diffy. All of them compare outputs. None compares structure, and none lets you declare which invariants have to survive. The gap is exactly there, and it is narrow.

2 What cannot be proved

There is no way — not with more computers, not with more time — to prove that two programs always do the same thing. That is a settled mathematical fact, not a limitation of this tool.

So this tool never says "it behaves the same". It says something smaller and true: you wrote down a list, and here is what happened to every item on your list.

Program equivalence is undecidable. "Behaviour is identical" cannot be proved and promising it is a lie. What can be proved is that the declared and extractable set of invariants survived — strictly weaker than the informal promise and strictly more useful, because it is checkable.

That wording is fixed in the model rather than in the renderer, and undecidable/1, scope_covered/1 and out_of_scope/1 are facts in the program, so the tool prints its own boundary instead of letting a reader assume it covered everything.

3 Two revisions, one reader

Before the change, a machine reads the code and writes down plain facts: which functions exist, which one calls which, what each file lets the outside world use. After the change, the same machine reads the new code and writes the same kind of facts.

Nobody judges anything while reading. Two lists, made the same way, and then they get compared.

Extraction is deterministic at both ends. scanners/js.ts — which already exists in this repository for other purposes — parses TypeScript into src_func, src_call, src_import, src_export facts and stops. It does not resolve an import specifier to a file, because a scanner that resolved imports would be a compiler, so resolution happens in rules instead, where it stays inspectable.

The two models go into two ledgers and the kernel keeps them apart. [before] is written by the freeze, [after] by the live re-extraction, [claim] by the engineer, and every conclusion lives in [main] and reads all three through declared imports. "Preserved" and "violated" are derived; nothing is ever filed under them.

The extractor version is the content hash of the extractor. Change the reader and the version changes by construction. Section 11 shows what happens when the freeze and the check disagree about it.

4 The list is written by a person

This is the one step a machine cannot do. Somebody has to say what kind of tidying this was, because that is what decides which things are allowed to move.

Renaming something is allowed to change names and nothing else. Moving a file is allowed to change where files live and nothing else. Pulling a piece of one function into a new function is allowed to change the inside wiring — but not what the program reaches out and touches.

Putting several kinds of tidying in one change costs you. You can only promise what all of them promise. The rename alone promised the wiring would not move; doing the rename and the extraction together gives that promise away, and the tool tells you so.

The catalogue of classes belongs to the tool — it is what the words mean. Choosing one belongs to the engineer, in [claim], and that separation is enforced rather than conventional: the extractor has no authority over [claim], so a tool that tried to declare its own equivalence class would surface as forged[audit], mechanically.

Each invariant is a set of ground tuples extracted the same way on both sides — a set of derived predicates, never a list of files. entry_effect is the (entry point, effect) pairs reachable from the front door; boundary is (module, exported name); module_dep is the import graph; entry_reach is which exported functions the entry point can still get to. The check is set difference over obs(Side, Invariant, Tuple).

5 The verdict

Two problems, one cause. While pulling a piece out of one function, the line that saves the order to the database came out with it and never went back. The order is still processed. The customer still gets a receipt. Nothing is ever written down.

The last block matters as much: most of the change did move things, and all of that was allowed. A checker that found nothing changed at all would not be checking anything.

Extracting applyDiscount out of settle() took the persist(order, receipt) call with it. The database write is no longer reachable from the entry point, and an exported function is no longer reachable either — two rows, one cause. Every test over this service still passes: handleOrder returns the same receipt.

Directions are per-invariant. entry_effect, boundary and module_dep are exact — gaining an effect reachable from an entry point is a behaviour change — while the rest are no-loss.

The useful answer is not "something is different". It is: here is the path the data used to take, and here is exactly the step that is missing.

Not "the diff did not match", but: the predicate is no longer derivable, here is the chain that derived it, here is the link that is gone.

7 What actually happens in the engine

This part is for people who want to see the gears. The short version: the whole thing is a list of "if this, then that" rules, applied over and over to a pile of facts until nothing new comes out. Then the same rules are run backwards to explain any answer.

Switch to Engineer above for the long version.

One evaluation of this world decodes 96 rules — 22 from boot.rofl, the meta-kernel, and 74 from ditto.rofl — and leaves 10,170 facts in the store, of which 5,836 are the kernel's own rule reflection and firing provenance rather than anything about the code. Every derived fact carries a derived_by(Fact, RuleId, Tick) record, emitted by the kernel with no cooperation from the program.

The strata, and why the order is load-bearing

boot.rofl computes the stratification as data: it derives dep/2, dep_neg/2, reach/2 and stratum/2 over the program's own reflection, and the kernel reads the table rather than containing a stratification checker. Over this program that gives 112 relations across 4 distinct strata, and the engine runs each negation phase to fixpoint before opening the next.

The recursion, and the reason it carries a chain

Reachability is asked twice, for two different questions. creach is the ordinary walk and it is the right boolean. It is the wrong thing to count: flattenLines in the fixture is recursive, so the graph is on a cycle, every trip round it is another derivation, and the counting semiring answers INFINITE — honest, and useless as a measure of redundancy. 

route[main](S, A, A, cons(A, nil))   :- node(S, A).
route[main](S, A, C, cons(C, Path))  :- route(S, A, B, Path), edge(S, B, C),
                                        fresh(S, C, Path).

So routes carry the visited chain inside the fact, the technique examples/nope uses for assume-role chains. fresh is positive rather than negated — the chain domain is generated by chain from the routes already derived — so this is ordinary monotone recursion over terms and the stratification checker never has to be argued with. It also has to be keyed by side: one route present in both revisions would otherwise give the same chain fact two derivations and double every count through it.

The shape of the why-tree

whynot is not a search for a reason. It is the rule set run backwards: for the queried literal it takes every rule that could conclude it, unifies the head, and for each one reports the premise instances that fail — then recurses into each failing premise. Read the block in section 6 as four levels:

  1. edge[main](after, settle, persist) — the queried literal;
  2. rule r87550593 — the one rule that concludes edge, with its body printed as stored. The rule id is a content hash of the canonical clause, so editing the rule changes the id and any prose quoting it stops matching;
  3. failed premise: calls[main](after,"orders.ts","settle","persist") — of the three premises, this is the one with no instance;
  4. the same treatment one level down, until it bottoms out at no rule concludes 'src_call' and no matching base fact exists — an extensional relation with no fact. That line is the answer.

Both bounds are hard stops that announce themselves: depth caps the levels and nodes caps the whole tree, and a truncated demonstration prints [depth limit N reached] rather than trailing off. Cycles are caught by a path guard and print [cycle].

How an agent interrogates it

The point of the whole arrangement is that a caller with no knowledge of this program can drive it with six queries:

  1. ? refused(R) — is the comparison admissible at all? If this is non-empty, stop: nothing below means anything.
  2. ? violated(I, T, D) — what broke, as tuples, with the direction (disappeared or appeared).
  3. ? route(before, Entry, B, Path) — the chains that carried it, with the path inside the fact so it can be printed directly.
  4. whynot on the corresponding after literal — the missing link, named, with the rule that would have concluded it.
  5. a provenance fold over the frozen fact — which extracted facts carried the invariant, and therefore where the loss can be. A counting fold over the same fact — how many independent routes carried it, and whether the survivor is now alone.
  6. ? probable_cause(A, B) — a ranked guess, explicitly a guess, with its evidence tiers.

And then the loop closes: fork the store, assert the repair, evaluate again, and read violated a second time. Nothing in that sequence requires the caller to have read ditto.rofl.

8 A guess, and the proof it stays one

Three calls vanished in this change. Two of them were meant to vanish and one was not — and the tool is not told which. It offers all three with a confidence score, and the real mistake comes out on top because there is more evidence for it: the thing it used to call is still there, still advertised to the outside world, and now nobody calls it at all.

It stays a guess. Nothing else the tool says leans on it.

Three tiers of evidence, each a separate derivation of hint, folded with the Viterbi semiring — which takes the best tier rather than the product, so confidence is the strongest evidence available and not what survives multiplying the weakest. The weights ride on the firing, so the ledger never carries a number nobody measured.

Two of the changes here were a rename and a moved file. Those touch everything that mentions the old name or the old place, so a tool that just compares the two lists screams that the whole program was rewritten. It has no way to know a rename is a rename — unless somebody tells it.

Telling it is two lines. And those two lines have to be right: take the rename line away and the tool immediately reports the tidy-up as a rewrite, which is the check proving it can say no.

The declared identification is renamed[claim]("findCustomer", "loadCustomer") and moved[claim]("db.ts", "storage/db.ts"). The map applies to [before] only, never to [after]: applying it in both directions would silently rewrite an unrelated new function that happened to reuse an old name.

Two invariants are deliberately raw rather than canonicalised — identifier and layout — because those are precisely what the maps are allowed to move. Canonicalising them would make a rename unfalsifiable.

The suite proves both directions. Delete the declared rename and boundary and entry_reach both fail; delete the declared move and module_dep and boundary fail. Two tests further on, two identical revisions violate nothing and all four invariants report HELD. A gate that has only ever answered one way is not a gate.

10 The invariant that held and lost its spare

One of the things this program does is write a line into a log every time an order goes through. Before the change, two different paths wrote that line — somebody thought that was wasteful and removed one.

The log line still gets written, so nothing is broken. But there used to be a spare and now there is not: the next person who touches the one remaining path can delete the log line entirely, and nothing will notice. That is a problem you can see today about a day that has not happened yet.

The counting semiring over effect_reachable: the value of the fact is the number of independent simple routes from the entry point to a site performing that effect. audit_write is not a violation — the declared invariant holds and the tool says so — and it has gone from two carriers to one.

Stating the reading is part of shipping the number. The identical count means robustness in examples/nope, ambiguity in AKA, fragility in examples/drip, and reserve here.

What the declaration cannot say. There is no way in this vocabulary to write "and the number of routes must not drop". Whether losing a spare should block a merge is a human call, and it is named here rather than quietly decided.

11 Proposing a fix, and refusing to answer

Once the tool knows which wire is missing, it can put the wire back in a copy of the model and check again, without touching anything real. Two violations become zero — so that really was the missing wire.

And the tool knows when not to answer at all. If the "before" list and the "after" list were written down by two different readers, comparing them says something about the readers, not about the code. So it refuses — including refusing to say everything is fine.

The control is printed because a per-fact cost is not portable: 5,836 of this store's 10,170 facts are rule reflection and firing provenance carrying nested terms, and they copy at about 1.6× the cost of a flat ground fact. Neither figure reproduces the ~3 µs/fact recorded for clone() elsewhere in this repository — and the flat control here does not either, so most of that gap belongs to the measurement rather than to this store. Printed rather than smoothed over.

12 The case this repository provided, the day this was written

This is not a made-up worry. On the day this page was written, three tidy-ups landed in the engine that runs all of this, and the way each one was approved was: take a photograph of the output before and after; if the photographs are identical, it is fine.

One of them really was fine. Another one passed the photograph test perfectly — identical, not one byte different — and was broken anyway, badly enough to give nine wrong answers elsewhere. The photographs could not see it because they were all taken of simple programs, and the broken part only showed up in a complicated one.

Three refactorings landed inside src/ on 2026-08-30, and the acceptance gate for each was literally a golden master: the goldens must move zero bytes.

  • The argument index rewrote much of src/store.ts. Goldens moved zero bytes, full suite green. A legal internal rebuild, correctly accepted.
  • The meta-layer cache passed its own fifteen tests, moved the goldens by zero bytes, and still broke nine tests in examples/wtf/ — a creature's characteristics computed as 2/2 where they should be 3/3. Wrong answers, not flakes. The goldens could not see it because every golden program stops at one to three strata and wtf carries fourteen.

The lesson recorded that day, in facts/findings.rofl: a golden is not a substitute for coverage, it is a substitute for a diff. The same evidence — "the goldens moved zero bytes" — was produced by a change that preserved what mattered and by a change that did not, and it could not distinguish them.

What a declared class would have caught here, and what it would not

It would not have caught the meta-cache bug. Both changes are legal internal rebuilds by DITTO's structural measure: Store's exported surface, the kernel's entry points and the effects reachable from them did not move in either case. A structural check over src/ would have said HELD for both — agreeing with the golden master, including the time the golden master was wrong.

What it adds is that the claim becomes falsifiable. Both authors made the same acceptance argument and neither had to write down what it meant. Written down, the meta-cache author's class is "the derived fact set of every loaded program is preserved; the internal structure of the meta layer is not" — a sentence that is false, and false in a way something can check. "The goldens moved zero bytes" cannot be false in any interesting way, because it says nothing at all about programs the goldens do not contain.

And it names where the check has to run: not over src/ but over the derived fact set of loaded programs, with [before] the pre-change evaluation and [after] the post-change one. That acceptance had already been written in prose in the finding that proposed the cache — cached must equal uncached, byte-identical, plus a negative test proving the cache can miss. It was implemented, it passed, and the bug went through anyway, because the programs it ran on were the shallow ones.

So the honest general statement, which is this example's own boundary: a declared equivalence class tells you WHAT to compare; it does not tell you WHAT TO COMPARE IT ON. Corpus coverage is an orthogonal axis and DITTO does not touch it.

What DITTO does catch is the other failure: a change whose structure moved while every sampled output stayed the same. That is the planted defect on this page, and it is the shape a golden master is blind to by construction rather than by bad luck — handleOrder returns the same receipt either way.

13 What it does not prove

The reader can only see calls it can follow by name. A call made through a variable, or decided while the program is running, is invisible to it — and it says so, with a count, instead of pretending the number is zero.

Five of fifty call sites are not placed. The call graph is a syntactic over-approximation: a call through an interface, a callback or a value is invisible to it, and on a codebase that dispatches dynamically that is not a rounding error.

It also does not replace tests and must not be sold as doing so. It checks a different dimension — structure and effects — where tests check outputs. Together they cover more than either.

14 Checked against things that are not the engine

A tool that only agrees with itself has proved nothing. So the same question is answered twice more — once by deleting the suspect line from the old model and re-running everything, and once by a short piece of ordinary code that shares the raw facts and none of the reasoning.

(a) deletes the base fact from the frozen model and re-runs the whole program from scratch: if the model is right about what carried the invariant, the obliged observations that disappear are exactly the ones the edit lost. (b) re-resolves both call graphs in plain TypeScript over the EDB relations, never touching a derived one. The suite also runs it on a fixture it has not seen, because an oracle that agrees on one fixture proves very little.

A rule outside range restriction is evaluated top-down; the boolean answers stay correct and every count above would then be folded over a different fact set than the verdicts describe. That is asserted, not assumed.
