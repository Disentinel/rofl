HUH — How'd yoU get Here

A shell pipe throws rows away at every step, and then forgets. This one doesn't: ask it about a row that should be in the answer and isn't, and it names the step that threw it away and the exact test that row failed.

Explained without jargon.

1 The thing we are asking about

A web server writes one line every time somebody asks it for a page. Here is a log of 2000 such lines, and the one-liner every engineer types to find out which URLs are breaking: 

cat access.log | grep 4xx | awk '{print $7}' | sort | uniq -c | sort -rn | head
     47 /api/v2/checkout

That command is five small machines standing in a row. Each one takes the rows it is handed, throws some away or rewrites them, and passes the rest to the next machine. At the end, one number comes out.

Five stages, each a total function on a stream. The output is an aggregate over the survivors, and the survivorship information is destroyed the moment each stage returns.

cat every line of the log 2000 rows
→
grep 4xx keep only broken requests 153 rows
→
awk '{print $7}' keep only the URL part 153 URLs
→
sort put equal ones together 153 URLs
→
uniq -c count each group 47 checkout

Two questions that number does not answer, and you always want both:

  • Which 47? Which lines of the log added up to it.
  • Where did mine go? You know a particular line is a checkout that failed. It is not in the 47. Which of the five machines threw it away?

The second question is the painful one. Once a row is thrown away it is gone; nothing kept a note. So people run the command again, and again, chopping the last machine off each time, trying to see where their row disappeared.

Two queries, neither answerable from the output:

  • why — the set of input tuples whose derivations contribute to this aggregate.
  • whynot — for an expected tuple that is absent, the stage and the predicate instance that made it absent.

The second is the expensive one in practice, and the usual method for it is bisection by re-execution: truncate the pipeline, re-run, eyeball. That is a linear search over stages, by hand, per question.

2 The pipe, rewritten as rules

So we wrote the same five machines a second way — as four rules, the kind of thing a logic engine can read. A rule says "this is true when all of these are true". Reading them out loud:

  • a line survives grep when it exists, and its number is at least 400 and at most 499;
  • a line survives awk when it survived grep, and we know what its 7th word is;
  • sort keeps everything it is given;
  • a URL gets a bucket when at least one line reached it carrying that URL.

The same pipeline as four Datalog rules over pre-tokenized facts. Rules in ROFL are not compiled: they are stored as facts in the same graph as the data (premise_lit / conclusion_lit), and the evaluator has no other source of rules. 

s_grep(N)    :- line(N), status(N, C), C >= 400, C <= 499.
s_awk(N, P)  :- s_grep(N), field(N, 7, P).
s_sort(N, P) :- s_awk(N, P).
s_uniq(P)    :- s_sort(_, P).

The host reads the log and emits three facts per line — line(N), status(N, C), field(N, 7, "…") — and that is the whole translation. Everything after it is inference.

Evaluation is bottom-up to least fixpoint, seminaive, with facts, rules and firings all processed in lexicographic order of their canonical serialization — so the same program on the same inputs yields a bit-identical store, tick log and provenance, whatever order anything was inserted in.

The load above is one tick: no @next, no negation, no perspectives. Nothing exotic is carrying the demo.

3 Where 47 comes from

Notice the last rule does not count anything. It only says a bucket exists. The counting happens somewhere else, and this is the trick worth understanding:

Every time a rule fires, the engine writes down a note: which rule, and which facts it used. So the bucket for /api/v2/checkout ends up with 47 separate notes attached to it — one per line that got there. The count is just how many notes there are. Nobody had to write a counting machine.

uniq -c is not a rule and does not need to be. Every firing is recorded as a witness — rule id plus the premise references it consumed (fact, negated, or builtin) — so the derived fact s_uniq("/api/v2/checkout") carries 47 witnesses in the support hypergraph, not one.

A semiring is then folded over that hypergraph. The Boolean fixpoint is untouched: annotation changes a fact's value, never whether it holds, so the engine runs first, unchanged, and the fold reads the support the store already recorded: 

v_0(f)     = base(f) if f is base, else zero
v_{n+1}(f) = loop ⊗ ( v_0(f) ⊕ ⊕_supports ( weight ⊗ ⊗_premises v_n(p) ) )

With ⊕ = + and ⊗ = × over ℕ ∪ {∞} you get the number of derivations — uniq -c. With ⊕ = ∪ and ⊗ = pairwise ∪ over sets of source facts you get which inputs a fact rests on. Neither semiring is named anywhere in src/: the kernel knows "a semiring", the instances live in runtime/semirings.ts, and each declares its own convergence discipline (bounded / closed / bounded-unfolding) so that "it did not converge" cannot be used to paper over three different situations.

5 Where did mine go? — whynot

This is the part that is worth the whole exercise. Line 102 of the log is a checkout request. You expected it in the 47. It is not there. Ask why it is not, and you get:

whynot is the mirror image, and it recurses. For a literal that does not hold, it takes each rule that could conclude it, walks the body under the head substitution, names the premise instances that fail — and then does the same to each of those. On a four-stage pipe that walk is the stage chain.

Read the last line. Line 102's number was 500, and the first machine only keeps numbers up to 499. 500 is not ≤ 499. Machine one threw it away, on that exact test. Nothing was re-run to find that out — the engine just followed the rules backwards.

Three guards make the recursion terminate and each announces itself in the output rather than truncating quietly: a literal already being explained above is marked [cycle], depth shapes the tree, nodes caps it outright.

6 Delete one line — excise

Last question: if you deleted one line from the log, what would change? Not "roughly" — exactly.

excise is a clean re-evaluation on the EDB minus one fact, and the diff against the current store is the blast radius. It is sound under multiple support by construction, because there is no incremental maintenance to be wrong about.

Four things disappear: the line itself and its trace through three machines. The bucket survives, because 46 other lines still hold it up, and the count moves by exactly one.

7 How do we know it is telling the truth?

Easy, and this matters more than anything else on this page: the real command already exists. So the demo runs it — the actual grep | awk | sort | uniq -c, in an actual shell, over the same file — and compares the two answers every time it runs.

HUH's ground truth is free and deterministic, so there is no excuse for asserting the engine is right instead of checking it. The demo spawns /bin/sh on the same file and compares: the full bucket table, the source line numbers behind a bucket (against grep -n), and the table after deleting one line (against awk 'NR != 96'). A disagreement would be reported as a finding, not reconciled by adjusting the engine's answer.

The same assertions run as a test (test/example-huh.test.ts) over a 400-line prefix of the same log, so the demo cannot rot: the counted result, the whynot chain down to the deciding builtin, the provenance set, and the excise blast radius are all checked against the shell on every run of the suite.

8 What this does not do

One honest catch. The engine has no idea what a word is — it only does whole facts and whole numbers. So the part that chops a log line into pieces is ordinary code, written by hand, outside the engine. The engine explains everything from the pieces onward, and stops there. You can see the floor in the second whynot above, on the last line: "no rule concludes 'field'" means this is where my explanations run out; a human's code decided that bit.

There are no string builtins in the kernel, and is is integer-only. So grep 4xx and awk '{print $7}' cannot be rules. The host splits each line and emits field(N, 7, "…"); the rules are the pipe over the split. This is architecturally right — it is what scanners/ exists for — but it costs something specific: the why-boundary sits one step higher than HUH's own sketch draws it. That sketch starts inside the line ("grep skipped 47 of 128340"); this one bottoms out at field(N, 7, P) as an axiom. Section 5's second tree shows the boundary in the open rather than hiding it.

  • The regex is not the shorthand. grep 4xx matches nothing literally; engine and oracle both use grep -E '" 4[0-9][0-9] ', anchored on the quote that closes the request so it can only match the status field.
  • sort -rn | head is presentation. v0 has no aggregation, so ranking the buckets is host-side sorting of the annotations. sort appears in the rules only as a nameable stage: order is not a fact here, so it is the identity on the multiset.
  • Provenance is capped at 32 source sets (PROVENANCE_MAX_TERMS), applied before superset pruning. The 47-line bucket therefore reports 32 of its 47 lines — a documented under-approximation, printed as such, and the reason the page lists sources for a bucket that fits under the cap. Counting is unaffected: one bigint per fact.
  • No cost claim. 2000 lines, one fixpoint, about a second on a laptop. That is a fact about this example, not a benchmark.
