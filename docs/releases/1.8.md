# ROFL 1.8 — release notes

Since `rofl-nb-1.7.0` (2026-11-15): #247–#304. Every line names the PRs that made it; what an agent must do
differently comes first. The 1.7 notes are kept in docs/releases/1.7.md, and their known gaps stand except where a
line here says one is closed.

## What an agent must do differently

1. **The JS model is `@js`** (#259). It is a library with a folder and a version of its own, `models/lang/js/`
   (`library(js, "1.0.0")`, `needs_engine(js, "1.7.0")`); write `@js` where 1.7 had `@rules/js.files`. An engine
   older than the model needs refuses it and names both versions.
2. **The memory is the wall, not 500 000 rows** (#276, #291). A world grows as far as the memory the process may
   use. A partial answer opens with `[partial answer: ...]`, ends with why and which flag moves it, and stderr names
   the largest directories to leave out; exit 5. A question longer than 15 s says every 15 s how far it has got.
3. **An answer says where each node is** (#297). A row whose value is a node is followed by `File:Line` and the
   text of that line; `--json` carries the same as `places` beside the rows. A script that read the rows line by
   line must skip the place lines.
4. **`rofl serve` watches and edits** (#275). `watch` and `unwatch` a relation's rows, `edit` takes facts and rules
   out and in in one request, a rule can be taken out; one path of retraction. docs/cli.md, *rofl serve*. This is
   what FKTS runs on; 1.7's package did not have it.
5. **Assumptions over a kept world** (#273, #280). `assumed_env[assume]("NODE_ENV", "production")` decides every
   test of that value; the branch not taken counts as never run, and `rofl excise` of the fact brings it back by
   delta, whole or by volumes.
6. **A why not over a corpus is a table of files** (#254). An open `whynot` that holds says how many answers and in
   how many files, then the files; `--in NODE` walks it in one file.
7. **`rofl scan` writes columns** (#259). 155 files of VS Code take 16.7 MB where they took 65.9 MB.
8. **The notebook asks the engine** (#251). The VS Code extension loads no engine; a notebook's first run takes
   about 1.7 s where it took 7 to 9.

## What changed since 1.7.0

**The JS model gives a value to almost every read** (#261, #281, #283, #287, #288, #290, #293, #295). A read is
*covered* when the model gives it a value, a named one or an open one (`may_be(E, open, W)`); a read with no value
answered short without saying so. Over all source files, no tests (`scripts/vscode_corpus.ts corpus`):

| project (files) | reads 1.7 | reads 1.8 | calls 1.7 | calls 1.8 |
|---|---|---|---|---|
| express (7) | 72% | 99.7% | 57% | 99.5% |
| axios (83) | 75% | 98.8% | 59% | 97.4% |
| vue core (283) | 95% | 99.4% | 90% | 99.5% |
| three.js (932) | 94.5% | 98.5% | 81.7% | 93.1% |
| react, first 800 of 1613 | — | 98.1% | — | 97.8% |

- #261 a call is an instance of what its function hands out, a method call of the instance it is called on;
  #281 a rest binds its name wherever its pattern stands.
- #283 patterns on the left of `=` and in `catch`, what a call runs (callbacks, executors, `f.call`), what a host
  member returns and puts, and the open value.
- #287 a for-in key used as a key again is open; `may_be_node` joined once. #288 a name nothing declares is the
  global of that name; a default import carries every kind; members of what the model does not keep are open.
- #293 a specifier is cut by the rules, so a string edit goes by delta (the scanner's contract changed: a corpus
  scanned for 1.7 is to be scanned again). #295 the literals of an input are read where a rule asks them.
- #286 the JS model writes no `[surface]` book.

**The engine** (#252, #256, #277, #278, #279, #284, #285, #292, #294, #296, #298, #303). A question over a kept world
opens only what its walk reads: on 1 000 files of VS Code a question about one value takes 0.10 s and 0.13 GB where
it took 3.6 s and 3.9 GB. An edit writes only what it moved: 4.2 MB an edit on 300 files, where it wrote 137.9 MB.
A corpus is read under the memory wall, each file's facts cut to disk; a unit cools whole under pressure. #294 an
edit by levels no longer loses what a group concluded from a fact its child holds; #303 a unit cooled under the
memory's pressure and settled again by an edit is written as a patch, not whole.

**Process** (#253, #255, #258, #264–#269, #274, #289): the merge train; what a world cost is blessed beside what it
answered (`golden_cost`); the product model and its invariants; a landed request is said by feature.

## 1.7 against 1.8, measured

Rust release build, 4 cores, 15 GB, VS Code at the pinned commit, `--space 400000000` for both (1.7 stops at
500 000 rows by default). The 1.8 engine answers every 1.7 world: 627 of 636 byte for byte, the other 9 differ only
in the proof's text (a view's rule is `_vN` where it was `~N`, and the view's premise is cited).

| question | files | 1.7.0 | 1.8 engine, 1.7 model | 1.8 |
|---|---|---|---|---|
| `side_effect_value` | 250 | 34 s, 0 answers | 32 s | 73 s, 10 answers |
| | 1 000 | 206 s, 10.4 GB, 1 590 | 185 s, 5.2 GB, the same 1 590 | no answer in 743 s: the 10 GB wall |
| asked again | 250 / 1 000 | 1.0 s / 4.2 s | 0.4 s / 1.2 s | 0.4 s / — |
| an edit, asked again | 250 | 29 s | 30 s | 52 s |
| `calls(A, B)` | 250 | 34 s, 9 439 rows | — | 97 s, 11 928 rows |
| | 1 000 | about 300 s, 31 337 rows | — | no answer in about 1 270 s: memory |

The engine is faster and holds half the memory. The JS model costs more because it covers more: from #283 on, the
same 250 files evaluate in about twice the time (27 s on the 1.7 model, 61 s after #283, 75 s after #295). 1.7's
0 answers at 250 files is its globals defect, closed by #288.

## Known gaps

- **The JS model at 1 000 files of VS Code does not answer on a 15 GB machine** (since #283). `side_effect_value`
  and `calls` stop at the memory wall and say so. The hottest rule is `sx_mwrite` (js-dataflow.rofl): a merge's
  sources read by `may_be_node` from a popular source; split in two it answers the same at 250 files, to be measured
  at 1 000 and shipped in 1.8.1. The 11 100-file reference is not measured on 1.8.
- Levels answer otherwise than the world whole where a rule reads a relation only one file states
  (`f_levels_drop_answers_beside_a_one_file_relation`); 1.7 has it too.
- A member of a known object at a key nothing writes (`const { Axios } = axios`) is still silent.
- What `new f()` returns is open, not carried: carried, three.js's constructors met in one function from thousands
  of calls and the run went past ten minutes.
