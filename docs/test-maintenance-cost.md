# The cost of the test suite, and what to do about it

## Status

Written 2026-09-09, after adding one node kind to the JavaScript model. The
change itself was small. Bringing the test suite back to green took most of the
elapsed time, and the work was almost entirely mechanical. This document
measures that and proposes changes. It is a criticism of the current test
design, not of testing.

## Why this is worth a document

The JavaScript modeling sessions cost roughly **US$5,000 in subscription
tokens** in total, per Claude Code's own accounting (figure reported by the
owner, not measured here). A large and identifiable share of that went into the
work below: re-measuring and restating derived totals in tests, none of which
was a change in behaviour. That is the argument for the proposal at the end —
not tidiness, but that the suite's current design charges a real price for every
routine change.

## The measurement

Adding `import_attribute` to the vocabulary — one node kind, five verdicts, five
rules, two audits and one fixture:

| | Lines changed |
| --- | --- |
| Model (`rules/`, `facts/`) | 220 |
| Tests | 338 |

Ten existing test files had to be edited. Thirty-two assertions were restated.
Of those, **not one was a change in behaviour** — every single one was a
derived total or percentage that moved because the vocabulary grew by one:

- 14 cell counts in `test/js-model.test.ts` (`91 → 92` kinds, and thirteen
  predictions derived from it);
- 7 row and derivation counts plus 1 threshold in `test/js-layer-cost.test.ts`;
- 2 in `test/js-fixpoint-cost.test.ts`, 1 in `test/js-callgraph.test.ts`;
- 4 named sets that legitimately gained an element.

The four named sets were quick and informative: each one gained exactly the
element the change added, so reviewing the diff confirmed the change. The
twenty-eight numbers were neither. They told me the vocabulary had grown, which
I already knew, and each had to be re-measured by running the suite, reading the
actual value out of a failure message, and pasting it back.

## Why this happens

Three separate anti-patterns, all common and all fixable.

### 1. Asserting derived global aggregates

`assert.equal(cells, 208)` is a test of the whole vocabulary crossed with the
whole layer list. Any change anywhere in either breaks it. It has one bit of
diagnostic value — "something moved" — and it costs a full suite run to restate.

The comments beside these assertions show the problem clearly: several read
`predicted 134` next to a literal `182`, because earlier authors moved the
number and left the explanation. A pin whose explanation has rotted is worse
than no pin: it invites the reader to trust a stale account of what the number
means.

**Remedy.** Assert the invariant, not the total. What these assertions actually
want to say is:

- the three verdicts partition the cells (`modelled + waived + not_modelled ==
  cells`) — an identity, true at any vocabulary size;
- there is one cell per (kind, layer) pair — also an identity;
- no cell lacks a verdict and no verdict lacks a cell — the existing audits
  already say this and they are already asserted empty.

All three survive a vocabulary change untouched. None of them needed restating
today. The totals added nothing on top of them.

### 2. Golden values written as literals instead of computed

One mutation test compares a computed percentage against `6.593` — the baseline
world's percentage, copied into the source. When unrelated work moved the
baseline, the test failed even though the mutant was still being caught, with a
larger margin than before.

**Remedy.** Measure the baseline in the same run and assert the difference
against a band. Nothing is then written down that the corpus can move, and the
test keeps testing the mutant rather than the corpus.

### 3. No distinction between numbers that are supposed to be stable and
numbers that are supposed to drift

The suite pins both kinds with the same `assert.equal`, so a reader cannot tell
which failures matter. Row counts and derivation counts drift with every model
change and are re-stated as a matter of routine. Answer counts — how many call
edges are resolved, how many cells are open — should be stable, and a change
means something.

**Remedy.** Separate them physically. Answer-shaped assertions stay in the layer
test files as ordinary assertions. Drift-shaped numbers go to a snapshot file
(one file, regenerated by a script, reviewed in the diff). Approval testing is
the standard name for this. A snapshot diff showing `world total 3065779 →
3066104` is exactly as informative as the assertion was, reviewable in one
glance, and costs nothing to update.

## Concrete proposal

In priority order, by time saved per unit of work:

1. **Move every world total, layer total, derivation count and percentage into
   one snapshot file** with a regeneration script. This alone removes about
   twenty-five of the thirty-two restatements measured above.
2. **Convert the remaining literal totals to identities** where an identity says
   the same thing — the verdict partition, one cell per pair, no orphans.
3. **Compute mutation-test baselines in the same run** rather than copying them
   into source.
4. **Keep named sets as they are.** They earned their place: they merge across
   branches as unions, they show which element changed, and three parallel
   branches modified the same sets today with no manual conflict resolution.

Expected effect on a change like today's: the four named sets would still need
editing, and they should. The twenty-eight numbers would become one snapshot
diff.

## What not to change

The mutation tests themselves are worth their cost. They caught real defects
this session, including three in their own oracles. The problem is not that the
suite checks too much; it is that a large part of what it checks is expressed as
a brittle literal when an identity or a snapshot would say the same thing and
survive routine change.
